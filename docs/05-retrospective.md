# 05 · 复盘与下一步

本文记录本次 AI 协作实现的技术复盘。候选人自己的学习经历、个人难点和亲自修改结果尚未提供，不在这里虚构。

## 最难的问题：让“有引用”确实有约束力

仅要求模型附带文档 ID，会遗漏三种常见问题：没有读过原文就引用；引用写 10 天而答案写 100 天；只看一个命中而忽略另一份冲突文档。

本次将这些风险变成运行时可验证的约束：引用只能来自成功读取的完整短片段，事实答案由引用渲染；同主题同范围的候选文档通过元数据关联，未补读就不能标记 answered。校验错误返回给模型，保留模型进一步选择动作的机会，而不是在最后静默改写结论。

代价是答案接近原文摘录、冲突判断较保守，仍需模型判断问题与证据是否相关。精确字符串校验与语义可靠性是两种不同能力，不能从前者的通过率推断后者。

## 实现过程中确认的认识

- 可观察性来自实际执行：先记录动作和真实返回，再生成可读 Trace；预设日志不能证明决策发生过。
- 重试属于模型下一轮动作。本地执行器故障后只返回错误，不自动修复为成功；因此能区分工具曾失败与任务最终恢复。
- 版本日期只能作为来源信息。没有范围或废止关系时，新日期不构成权威优先级。
- DeepSeek 的兼容接口仍有专用参数；接口契约测试能发现请求格式问题，但无法证明真实模型会作出正确决策。
- 修改资料是有价值的回归检查：10 改为 12 应改变答案，冲突消失应改变后续动作。这比只重复同一条成功路径更能发现答案或流程写死的问题。
- 真实运行暴露了评估断言过窄的问题：等价原文可来自两份文档，不能要求模型只引用预定的一份。修正检查时应保存原始 10/11 结果，并用同一批记录重评，不通过改写 Trace 获得“通过”。
- 本轮 5 次协议响应错误均能根据反馈恢复，但会消耗预算；其原始响应 ID/用量未保留是现有审计短板，不能把已保存的 token 合计当作完整成本。

## 范围控制与下一步

在建议的 3 小时尺度内，优先完成 CLI 核心链路和验收材料。没有为界面、框架包装或部署增加工作。实际 AI 协作墙钟时间见 [work-log.json](work-log.json)；个人投入需本人记录。

后续按价值排序：

1. 真实 DeepSeek 验收与至少两条不同路径已完成。下一轮使用未见问题重复运行，保留协议错误响应的安全元数据，评估恢复是否稳定。
2. 用未参与调试的问题、不同问法和重复运行检验稳定性，特别是适用范围不明确、命中噪声、部分资料缺失与参数出错的情况。
3. 若真实运行暴露问题，先修改提示词/检索并比较前后 Trace；由候选人亲自解释一项修改及验证结果。
4. 文档数量扩大后再引入语义召回、重排与检索评测；维护明确的适用范围、废止和权威关系，逐步减少保守误报。
5. 仓库已推送到指定 GitHub 的 main 分支；提交评审时确认访问权限，并提供该分支最终 SHA。
